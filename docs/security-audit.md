# Security audit (Slice 3)

## Scope and evidence limits

Reviewed `database/01_schema.sql`, `database/02_functions.sql`, `database/03_policies.sql`, `src/main.js`, and `src/supabase.js`. The required `AGENTS.md` and frozen `SLICE_3_SPEC.md` are absent from this checkout, so I could not determine which current behaviors the frozen spec explicitly fixes or whether any implementation conflicts with it. “Fixed by frozen spec” therefore cannot be asserted for any finding below; the code/SQL status is stated directly.

The frontend calls Supabase for these tables: `profiles`, `packages`, `food_categories`, `food_items`, `package_food_items`, `package_categories`, `bookings`, `booking_food_items`, `booking_cancellation_requests`, and `notifications` (`src/main.js:130,207,226,234,243,246,256,286,288,330,374,611,706,790,795,859,960,1058,1098,1115,1131,1165,1206,1223,1413,1456,1479,1482,1577,1599,1634,1650,1673,1677,1741,1759,1886,1921,1937`). RPC: `review_booking_cancellation_request` (`src/main.js:1383-1389`). The first eight tables have RLS enabled and policies in `database/03_policies.sql:3-41`; `notifications` and `booking_cancellation_requests` are used by the app but absent from all three supplied SQL scripts. The RPC is invoked by the app but is not defined in `database/02_functions.sql`.

## Findings

| ID | Severity | File:line | Description | Recommended fix |
|---|---|---|---|---|
| S3-01 | High | `src/main.js:283-288`; `database/02_functions.sql:1-68` | Booking pricing is authoritative only in the browser: `priceData()` values are used to calculate `base`, `extra`, `per`, and `total`, and those client-supplied amounts are inserted directly. SQL has arithmetic consistency checks (`database/01_schema.sql:115-119`), but no `create_booking` RPC or server recomputation exists in the supplied functions file. A caller can submit internally consistent but fabricated prices. | Implement/require a server-side booking RPC that loads active package and selected food prices, validates menu rules, and computes all price fields; deny direct client inserts to bookings and booking food details. **Open in inspected code; frozen-spec status unverifiable.** |
| S3-02 | High | `src/main.js:286-288`; `database/03_policies.sql:29-38` | Booking row and menu details are two separate PostgREST requests. If the second insert fails, the booking remains, and the UI explicitly reports that partial state. They are not atomic. | Insert booking and detail rows within one database function/transaction and call only that function. **Open in inspected code; frozen-spec status unverifiable.** |
| S3-03 | High | `src/main.js:130,611,706,1058,1098,1115,1165`; `database/03_policies.sql:1-41` | App reads/writes `notifications` and `booking_cancellation_requests`, but neither table is created, RLS-enabled, or given policies in the supplied schema/policy scripts. Cancellation review RPC is also called at `src/main.js:1383-1389` but absent from `database/02_functions.sql`. The relevant application paths cannot be secured or shown functional from these scripts. | Add schema, enable RLS, define least-privilege owner/admin policies and the reviewed RPC; otherwise remove the unsupported calls. **Open in inspected SQL; frozen-spec status unverifiable.** |
| S3-04 | Medium | `src/main.js:1413` | The admin search term is interpolated into PostgREST `.or()` filter syntax (`ilike.%${term}%`). A user-controlled term containing commas, parentheses, or filter operators can alter the filter expression. This is filter injection rather than SQL parameter injection. | Escape/encode PostgREST filter grammar metacharacters, or use a server-side search function with bound parameters. **Open in inspected code; frozen-spec status unverifiable.** |
| S3-05 | Medium | `src/main.js:284`; `database/01_schema.sql:78` | Booking references are generated from `Date.now()` (`JM-` plus base-36 timestamp), making them predictable and potentially colliding under concurrent submissions. The column is unique, but uniqueness does not make references unguessable. The tracking lookup by reference at `src/main.js:330-351` makes this relevant to enumeration risk; access control must be checked separately. | Generate a cryptographically random reference server-side and enforce authorization on lookup; avoid using a reference as a bearer credential. **Open in inspected code; frozen-spec status unverifiable.** |
| S3-06 | Medium | `src/main.js:223,1413`; `database/03_policies.sql:1-41` | `requireAdmin()` checks the profile role in the UI (`src/main.js:223`), but UI checks are not authorization boundaries. RLS is the actual data boundary; the supplied SQL has admin policies based on `is_admin()` for managed tables. However, the app's `notifications` and cancellation tables have no supplied RLS policies (S3-03), and no policy exists here for executing the cancellation review RPC. | Keep UI gating for usability, but enforce each operation in RLS or a narrowly granted security-definer RPC that checks `is_admin()` server-side; include all used tables/functions. **Partially covered for declared tables; gaps remain as in S3-03. Frozen-spec status unverifiable.** |
| S3-07 | Low | `src/main.js:9,1413` | `esc()` HTML-escapes values and is used for many rendered database fields, but it does not protect values interpolated into the `.or()` filter grammar. Some interpolations are numeric/database IDs (for example `data-status`), while the primary user-text locations reviewed generally call `esc()`. The search-filter issue is tracked separately in S3-04. | Continue escaping at HTML sinks and apply context-specific validation/escaping to query filter syntax; do not treat HTML escaping as universal sanitization. **Partially mitigated at HTML sinks; filter issue open.** |
| S3-08 | Low | `src/supabase.js:2-3`; `src/main.js:1-1966` | Frontend configuration references only `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`; no `service_role` reference was found in frontend source. These are public browser credentials, so authorization must come from RLS/RPC controls. | Keep service-role credentials out of Vite-exposed variables and browser bundles. **No secret exposure found in reviewed frontend.** |

## Fixed by frozen Slice 3 spec vs. open

The frozen spec file was not present, so this audit cannot responsibly label any issue as fixed by that spec or cite a spec line. In inspected code, server-authoritative pricing, transactional booking plus menu insertion, policies for notifications/cancellation tables, safe filter construction, and unpredictable server-generated references remain open. The declared tables do have RLS enablement and policies in `database/03_policies.sql:3-41`; the frontend uses only the anon key and project URL in `src/supabase.js:2-3`.
